# What this is

A config-driven, agent-agnostic **closed loop** that lets a coding agent implement a
task list autonomously, gated by checks it cannot talk its way past, and reviewed by a
human only at the PR.

`checks/` is the gate (typecheck, lint, tests, mutation, optional LLM review — all
driven by `.harness.json`). `loop/` is the driver: pick a ready task, run the agent on
it, verify, commit or retry, repeat. `templates/` is what gets copied into a target
project (the Claude Code hook layer, sample config, task/memory file formats).

This file describes the **principles the harness embodies**, so that an agent working
on the harness itself (or generating a harness for a new project) preserves them rather
than re-deriving or accidentally violating them.

# Principles

**1. Orchestrate, don't implement (in the same context).**
The agent that decomposes a spec into tasks and the agent that writes the code for one
task are different invocations. Planning produces `tasks.json`; each task is implemented
in its own fresh, scoped run. This keeps each implementation context small and on-task,
and keeps the human's one cheap review checkpoint — approving `tasks.json` — separate
from the expensive autonomous part.

**2. The gate must be something the agent cannot argue with.**
Not a review comment, not "I tested this and it works," not the agent's own report of
success. The gate is the compiler, the type system, the linter, the test suite, and
(optionally) mutation testing and a separate review pass — run independently by the
loop after every attempt. A task is "done" when the gate says so, never before.
`checks/gate.sh` (per-task) and `checks/gate-full.sh` (final) are that bar.

**3. Closed loop, not open loop.**
The loop runs inside a frame set in advance: a goal (`tasks.json`), defined steps (one
task = one bounded unit of work with `owns` and `acceptance`), a check at every step
(the gate), and a point where it stops or hands back to a human (PR, or `blocked` after
N failed attempts). It does not roam. Iteration count, wall-clock time, and cost are all
bounded (`HARNESS_MAX_ITERS`, `HARNESS_DEADLINE_MIN`, `HARNESS_BUDGET_USD`) — an
open-ended "improve this codebase" goal is the wrong shape for this harness.

**4. A failed attempt must be cheap and clean.**
On gate failure, the loop `git reset --hard && git clean -fd`s and retries with the
gate's stderr fed back as context (Reflexion-style). A run that changes nothing is
treated as a failure too (silent-failure / no-progress detection), never a free pass.

**5. Maker ≠ checker.**
The deterministic gate is the primary checker and is structurally separate from the
agent that wrote the code. Where the gate can't judge (does this test actually constrain
behavior? is this the right architectural call?), an optional separate review pass
(`commands["code-review"]`, mutation testing) fills the gap — still never the same
invocation that wrote the change.

**6. Memory lives on disk, not in the conversation.**
`tasks.json` is the goal and current state. `CLAUDE.md` (or `RULES.md`) is durable,
human-curated project knowledge — the loop can draft entries via `REFLECTION.md`, but a
human promotes them, and where possible a promoted rule becomes an enforced lint/test
rule rather than just prose, so "a mistake caught once becomes a wall forever." Git
history is the audit trail. The loop is restartable from any of these with no
conversational context.

**7. Everything stack-specific is config, not code.**
`checks/` and `loop/` are language- and agent-agnostic. What to run for typecheck/lint/
test/mutation/review, which paths are source, which commands are forbidden — all of
that lives in `.harness.json` (generated by `loop/loop.sh --init`, then reviewed by a
human). Adding support for a new language or coding agent should mean editing config and
adding an adapter, not branching the core scripts.

**8. The human's role is judgment, not supervision.**
No approval gates mid-loop (the loop runs unattended with full permissions, bounded by
the guards in `.harness.json`'s `blocked_command_patterns` and `source_globs`). The
human reviews the PR: task statuses, anything that needed multiple attempts, surviving
mutants, and code-review notes are surfaced there as a triage map — the gate already
guarantees correctness on the axes it can check.

# Provenance

These principles synthesize two sources: Addy Osmani's piece on orchestrating coding
agents (the orchestrator/implementer split, deterministic guardrails as the real
contract with an agent) and Daniel Moka's "Loop Engineering 101" (closed vs. open loops,
the six building blocks of a closed loop — automations, worktrees, skills, connectors,
subagents, memory — and "a loop that learns" via a human-owned rules file backed by
deterministic checks). Where the harness diverges from either source, it's because the
determinism goal won: e.g. `/goal`/`/loop`-style native agent loops were replaced with
this external driver because their completion checks can be conversational rather than
gate-based.
