# Autonomous-implementation harness — config-driven, agent-agnostic, project-agnostic

A loop you own, not a vendor primitive (`/goal` / `/loop`). Correctness = an external shell gate;
iteration = an external loop; everything stack-specific lives in **`.harness.json`**, generated by `--init`.

```
checks/      Verifiable gate. Reads .harness.json. Project- AND agent-agnostic. Source of truth.
loop/        Agent-agnostic driver + adapters + init. Owns iteration/budget/reset/PR/review.
templates/   Files you copy into a target project: .claude/ (Claude Code enhancement layer,
             optional), .harness.json, CLAUDE.md, tasks.example.json, package.scripts.json.
```

## Two roots
- `HARNESS_HOME` — where `checks/` and `loop/` live (this repo, resolved from the script path).
- `REPO` — the target project (`--repo PATH`, else git toplevel, else cwd).

They can be the same dir (copy this repo's contents into the project) or different (run the
harness against any repo from outside it — clone this repo once, point it at many projects).

## .harness.json (the only stack-specific surface)
```json
{
  "commands": { "typecheck": "...", "lint": "...", "test": "...", "test_related": "...",
                 "format": "...", "lint_file": "...", "pattern_check": "", "mutation": "",
                 "code-review": "" },
  "source_globs": ["src","apps","packages"],
  "test_file_exts": ["ts","tsx"],
  "package_manager": "bun",
  "blocked_command_patterns": ["npm ","yarn ","pnpm ","npx "]
}
```
- `commands` are run verbatim by the gates (empty/missing = skipped).
- `test_related` gets changed files appended (scoped tests); falls back to `test` when nothing matches.
- `mutation` runs only at the final gate (`HARNESS_RUN_MUTATION=1`) — surviving mutants get surfaced
  in the PR as a review map (tests that don't actually constrain behavior).
- `code-review` runs after a task's gate passes, before commit — see "Code review" below.
- `source_globs` → orchestrator-guard's deny scope (PLAN role can't write here).
  `blocked_command_patterns` → bash-guard policy. `pattern_check` → optional command for
  architectural invariants your linter can't express.

### Generate it
```
loop/loop.sh --init [--repo PATH]
```
Detects Node/Bun/pnpm/yarn/npm (+ ESLint/Biome/Prettier/Vitest/Jest/Stryker, React→tsx), Python
(mypy/ruff/black/pytest), Go (vet/golangci-lint/test/gofmt), Rust (check/clippy/test/fmt). Prefers
existing `package.json` scripts. Backs up any existing config to `.harness.json.bak`. Review the
output — empty commands mean detection missed; fill them in.

## Run
```
AGENT=claude loop/loop.sh my-feature              # in-repo
AGENT=codex  loop/loop.sh --repo ../other my-feat # out-of-tree, different agent
HARNESS_MAX_ITERS=1 HARNESS_BUDGET_USD=5 loop/loop.sh dry-run   # dry run first
```
Loop: pick ready task ▶ agent run (+ prior failure feedback) ▶ no-progress check ▶ `checks/gate.sh`
▶ code-review (if configured) ▶ commit / reset+retry ▶ block after N ▶ when queue empty: full gate
(incl. mutation) ▶ push ▶ PR (draft if red).

## Code review
If `commands["code-review"]` is set, after a task's deterministic gate passes the loop pipes a
payload (task, acceptance criteria, changed files, diff) to it. The reviewer's job is everything
the gate can't check: correctness vs. acceptance criteria, vacuous tests, edge cases, security,
architectural fit. Verdict is `CODEREVIEW: PASS` or `CODEREVIEW: CHANGES_REQUESTED` as the final
line (or a non-zero exit). Changes-requested feeds back into the same task's retry, bounded by
`HARNESS_MAX_TASK_RETRIES`. `checks/code-review.sh` is the default wrapper (calls `claude -p`,
override with `CODE_REVIEW_CMD`). Leave the key unset to skip this step entirely.

## Install (copy into your project)
```
cp -r templates/.claude templates/.harness.json templates/CLAUDE.md /path/to/project/
cp templates/tasks.example.json /path/to/project/tasks.json   # then edit for your spec
```
`package.scripts.json` is a TS/Bun/React reference for what `commands.*` typically map to —
optional; `--init` derives `.harness.json` directly, no package.json scripts required.

## Three ways to run it
1. **Copy-in** — copy this repo's `checks/`, `loop/`, and the `templates/` contents into the
   target project. Simplest; `HARNESS_HOME == REPO`.
2. **Out-of-tree** — keep this repo where it is; `loop/loop.sh --repo /path/to/project ...`.
   The target project still needs its own `.harness.json` (`--init`) and `tasks.json`.
3. **Claude Code plugin** — `templates/.claude/` can be packaged as a plugin (bundle `checks/`,
   resolve `${CLAUDE_PLUGIN_ROOT}`) so the L2 hooks install once across projects. Not packaged
   in this repo yet; the hooks are already portable (`${CLAUDE_PLUGIN_ROOT}` / `${CLAUDE_PROJECT_DIR}`
   fallback) if you want to build that.

## Generalizing to a new stack
Usually just `loop/loop.sh --init` then eyeball `.harness.json`. The architecture is
language-neutral; only the command strings and two guards (`blocked_command_patterns`,
`source_globs`) are stack-specific, and all of it is in the config. Project-specific *patterns*
(e.g. component-lib boundaries) stay in that project's linter — the harness runs it, doesn't
define it.

## Agent-agnostic
Swap agents via `loop/adapters/<agent>.sh` — a two-function contract: `agent_run "<prompt>"`
(run headless, edit CWD, echo raw output) and `agent_cost` (stdin→USD). Claude/Codex/Cursor/Gemini
stubs included; verify each CLI's flags. Non-Claude agents run on `checks/`+`loop/` only (no
in-session hooks) — the outer loop re-runs the gate and feeds failures back, so it's still fully
gated; they just lose the in-session force-continue and the unattended Bash guards (lean on each
agent's own sandbox/branch isolation).

## Loop-engineering guardrails present
Hard iteration cap, wall-clock deadline, cost budget (`HARNESS_BUDGET_USD`), per-task circuit
breaker, no-progress/silent-failure detection (empty diff ≠ success), external goal verification,
feedback-on-retry, optional LLM code review, mutation testing, human-at-PR.

Open: re-plan on block, periodic spec reconciliation, automations/heartbeat (this harness is the
*implementation* step — triggering it from an issue/CI event is left to the caller).

## Budgets (env)
`HARNESS_BUDGET_USD` (0=∞) · `HARNESS_MAX_ITERS` (30) · `HARNESS_DEADLINE_MIN` (480) ·
`HARNESS_MAX_TASK_RETRIES` (3) · `HARNESS_MAX_TURNS` (60) · `HARNESS_MAX_STOP_RETRIES` (5, L2).

## Verify before first real run
`jq` + your project's toolchain + `gh` + your agent CLI on PATH. Confirm `.harness.json` commands
actually run in your repo, and that codex/cursor/gemini adapter flags and `agent_cost` parsing
match your installed versions.
